# Content Area -- AIHealthcare Reference

> Last updated: 2026-10-05

The Content Area is the day-to-day reading and research surface of the app. It covers the news feed, article search, knowledge wiki, trend analysis, watchlist alerts, and newsletter management. Most of these pages are what paying subscribers interact with most -- they are how the harvested and AI-processed data becomes usable intelligence. The newsletter management pages are admin-only. The wiki index is fully public.

---

## Pages

### `/dashboard`

**What it shows:** A four-widget landing page: today's headlines, trending keywords, regulatory watch, legal pulse, and (when the user has configured items) watchlist alerts. A URL query string (`?q=`) activates inline article search.

**Data sources:**
- `news_articles` table -- 7-day window via `ArticleIngestionPort.fetchRecentArticles(7)`, capped at 8 headlines, deduped by lowercased title within the same calendar day
- `trend_snapshots` table -- top 5 rising signals from the latest persisted snapshot via `DetectTrendsUseCase.getLatestSnapshot()`; falls back to a live `TrendDetectionService.detectTrends()` call against 7-day articles if no snapshot exists
- `regulatory_events` table -- 3 most recent events via `MonitorRegulatoryEventsUseCase.getRecentEvents(3)`
- `news_articles` filtered by topic `"AI Healthcare Legal"`, capped at 3, via `ArticleIngestionPort.fetchByTopicWithArchiveLimit()`
- `watchlist_items` and `watchlist_matches` tables -- `WatchlistPort.findByUser()` and `WatchlistMatchPort.findByUser()` (5-match cap on dashboard); only rendered when the user has items with matches
- Inline search: `SearchArticlesUseCase.search()` run twice (title + body), merged and deduped, capped at 10 results

**Access / tier gating:** No content gates on the widgets themselves. The watchlist section only appears when the user has configured items with recent matches. The tier object is passed to the template for conditional UI, but no widget is hidden by tier.

**How data gets here:** Articles arrive via `FeedHarvestScheduler` (RSS, daily 04:00 UTC), `WebMonitoringScheduler` (competitor pages, daily 05:00 UTC; HuggingFace, 05:30 UTC), and `ResearchHarvestScheduler` (Perplexity, daily 04:00 UTC). Regulatory events arrive via `RegulatoryHarvestScheduler` (daily 04:30 UTC). Trend data arrives via `TrendDetectionScheduler` (weekly, Sunday 08:00 UTC). Watchlist matches are written immediately after each RSS harvest cycle by `WatchlistMatchingService`.

### `/dashboard/news`

**What it shows:** All active topics listed in order, each with its recent articles and a one-paragraph AI-generated summary (when 2 or more articles exist for that topic).

**Data sources:**
- Topic list from `NewsTopicProperties` (YAML key: `aihealthcare.topics`)
- `news_articles` table per topic via `ArticleIngestionPort.fetchNewsHeadlines(topic, archiveDays)`
- `topic_summaries` table via `TopicSummaryPort.findByTopic()` -- one summary per topic, generated post-harvest

**Access / tier gating:** Archive depth is gated by `TierGatingService.archiveDaysFor(tier)`. FREE users see a limited date window; SUBSCRIBER and ADMIN users get unlimited history (`archiveDays=0`). The template renders an upgrade prompt when the user is on a limited tier. One hardcoded title filter silently drops any article whose title exactly equals `"Anthropic Healthcare AI"`.

**How data gets here:** Same article pipeline as `/dashboard`. Topic summaries are generated by `TopicSummaryGenerationService` immediately after each RSS harvest (triggered from `FeedHarvestScheduler`).

---

### `/dashboard/articles`

**What it shows:** All articles for a single topic, no date limit, with body text stripped and truncated to 200 characters.

**Data sources:**
- `news_articles` table via `ArticleIngestionPort.fetchAllByTopic(topic)`, deduped by title + calendar day, sorted by `publishedAt`

**Access / tier gating:** The `"New AI Healthcare Companies"` topic is gated -- FREE and FREE_PENDING users see an `accessDenied` flag and an empty article list. All other topics are open to any authenticated user.

**How data gets here:** Same article pipeline as `/dashboard`.

### `/dashboard/search`

**What it shows:** A search form with filters for title, topic, author, source name, body text, and date range. Results update in-place via HTMX (returns a partial fragment when `HX-Request` header is present).

**Data sources:**
- `news_articles` table via `SearchArticlesUseCase.search(ArticleSearchCriteria)`, which applies a JPA `Specification` against all indexed fields

**Access / tier gating:** No tier gating at the controller level. Any authenticated user (including FREE) can search the full article corpus with full date range access.

**How data gets here:** Same article pipeline as `/dashboard`.

---

### `/wiki`

**What it shows:** A paginated, searchable index of all compiled wiki pages. 20 pages per page, sorted by last updated. Supports keyword search and page type filter.

**Data sources:**
- `wiki_pages` table via `WikiPageRepository`, using a lightweight projection (`WikiPageIndexView`) that excludes `contentMarkdown` and source refs for performance

**Access / tier gating:** Fully public -- no authentication required. This is intentional for SEO.

**How data gets here:** Wiki pages are compiled from harvested articles by `WikiCompilationAdapter`, triggered after each RSS harvest cycle by `FeedHarvestScheduler`. Manual compilation is also available via `POST /monitoring/wiki/compile`.

---

### `/wiki/{slug}`

**What it shows:** A single wiki page with rendered markdown content, source provenance table with evidence grades, contradiction history, related pages, revision history, and (for authenticated users with full access) analyst notes.

**Data sources:**
- `wiki_pages` and `wiki_source_refs` tables via `WikiQueryPort.getPage(slug)`
- Source article titles and URLs resolved from `news_articles` via `NewsArticleRepository.findByArticleIdIn()`; PubMed IDs construct URLs directly without a DB hit
- `wiki_contradictions` table via `WikiContradictionRepository.findByPageSlug()`
- `wiki_page_revisions` table via `WikiPageRevisionRepository.findByPageSlugOrderByRevisionDesc()`
- Related pages resolved one-by-one via `WikiQueryPort.getPage(relatedSlug)` (N+1 pattern)
- `analyst_notes` table via `AnalystNotePort.findByUserAndTarget()` -- authenticated users only

**Access / tier gating:** Requires authentication (enforced by Spring Security; unauthenticated visitors are redirected to register, making every external wiki link a registration funnel). `fullAccess` (SUBSCRIBER, DEMO, ENTERPRISE, or ADMIN) unlocks analyst notes. FREE users see the full page content but not notes.

**How data gets here:** Same wiki compilation pipeline as `/wiki`. Source articles come from the standard article harvesting pipeline.

### `/wiki/contradictions`

**What it shows:** A feed of all detected contradictions across all wiki pages, defaulting to the last 90 days (`?days=` param overrides). Each contradiction shows the prior claim, the new claim, their source articles, and a link to the affected wiki page.

**Data sources:**
- `wiki_contradictions` table via `WikiQueryPort.recentContradictions(since)`
- Source articles resolved from `news_articles` via `NewsArticleRepository.findByArticleIdIn()`
- Page titles resolved via `WikiQueryPort.getPage(pageSlug)` per contradiction (N+1 pattern)

**Access / tier gating:** Accessible to any authenticated user. `fullAccess` flag (SUBSCRIBER, DEMO, ENTERPRISE, ADMIN) is passed to the template for conditional rendering. FREE users see the page but may see reduced context depending on template gates. No hard redirect.

**How data gets here:** Contradictions are detected during wiki compilation by `WikiCompilationAdapter`. The CI-42 claim tracker can also write to `wiki_contradictions` via the auto-upgrade pipeline.

### `/newsletter/runs`

**What it shows:** A list of all newsletter runs with status badges (DRAFT / SENT / ARCHIVED), sortable by generated date, title, week-of date, or status. Also shows the current auto-send override state for today.

**Data sources:**
- `newsletter_runs` table via `NewsletterRunPort.findAll()` (all runs, no tier filter)
- Auto-send override state via `NewsletterAutoSendPort.isOverriddenForDate(LocalDate.now())`

**Access / tier gating:** No tier check in the controller. Access is restricted to ADMIN by Spring Security configuration.

**How data gets here:** `NewsletterGenerationScheduler` runs daily at 00:00 UTC (midnight) and writes a new DRAFT run to `newsletter_runs`. It does not auto-send.

---

### `/newsletter/runs/{runId}/edit`

**What it shows:** A TinyMCE 7.9.0 WYSIWYG editor pre-loaded with the stored HTML content of a run. Save and Send buttons.

**Data sources:**
- `newsletter_runs` table via `NewsletterRunPort.findByRunId(runId)`

**Access / tier gating:** ADMIN only (Spring Security). The controller renders the editor regardless of run status (DRAFT, SENT, or ARCHIVED); the template is expected to visually disable editing for non-DRAFT runs.

**Mutations:**
- `POST .../save` -- updates `htmlContent`, regenerates `plainTextContent` via `Jsoup.parse(html).text()`
- `POST .../send` -- calls `DeliverNewsletterUseCase.deliver(runId)`, then resets the auto-send override for today

### `/dashboard/trends`

**What it shows:** A Chart.js bar chart of the top 10 rising keywords, plus cards for rising, fading, and new keyword signals with linked article examples. When no persisted snapshot exists, falls back to a live computation.

**Data sources:**
- Primary path: `trend_snapshots` table via `DetectTrendsUseCase.getLatestSnapshot()`
- Fallback path: `news_articles` via `ArticleIngestionPort.fetchRecentArticles(7)` (or a custom date range via `fetchArticlesByDateRange()`), then `TrendDetectionService.detectTrends()` computed live and not persisted

**Access / tier gating:**
- Normal path (snapshot exists): FREE users see the top 5 rising topics (`FREE_RISING_LIMIT = 5`); SUBSCRIBER, DEMO, ENTERPRISE, and ADMIN see the full signal list
- Fallback path (no snapshot): only ADMIN gets `fullAccess=true`; SUBSCRIBER and DEMO users are treated as limited until the weekly scheduler runs

**How data gets here:** `TrendDetectionScheduler` runs weekly on Sunday at 08:00 UTC. It analyzes articles across 30/90/180-day windows and writes one `TrendSnapshot` per run via `TrendOrchestrationService.detectAndSave()`.

---

### `/dashboard/trends/history`

**What it shows:** A multi-line Chart.js chart of the top 10 keywords across all snapshots, plus a timeline table linking to individual snapshot detail pages.

**Data sources:**
- `trend_snapshots` table (all records, newest first) via `DetectTrendsUseCase.getAllSnapshots()`
- Cross-snapshot keyword frequency is computed in memory to determine the top 10 chart keywords
- Summary table uses the `TrendSnapshotSummary` DTO (epochMillis, timestamp, risingCount, newCount, totalKeywords, windowDays)

**Access / tier gating:** FREE users see the last 4 snapshots (`FREE_SNAPSHOT_LIMIT = 4`); SUBSCRIBER, DEMO, and ADMIN see all. The slice happens before chart data is built, so FREE users' chart also reflects only their permitted snapshots.

**How data gets here:** Same `TrendDetectionScheduler` as `/dashboard/trends`.

---

### `/dashboard/trends/history/{epochMillis}`

**What it shows:** The full detail of a single historical trend snapshot -- rising/fading/new signal cards with article links.

**Data sources:**
- `trend_snapshots` table -- full scan via `DetectTrendsUseCase.getAllSnapshots()`, matched by `epochMillis` comparison (O(n) linear scan)

**Access / tier gating:** No independent tier check. Access inherits from the parent history page.

**How data gets here:** Same `TrendDetectionScheduler` as `/dashboard/trends`.

---

### `/watchlist`

**What it shows:** The user's configured watchlist items grouped by type (COMPANY, KEYWORD, TOPIC), plus a table of recent article matches with snippets and links.

**Data sources:**
- `watchlist_items` table via `WatchlistPort.findByUser(email)`
- `watchlist_matches` table via `WatchlistMatchPort.findByUser(email, 50)` (50-match cap)
- Article titles and URLs resolved from `news_articles` via `NewsArticleRepository.findByArticleIdIn()`

**Access / tier gating:** Hard gate. The controller checks the user's tier via `SubscriberPort.findByEmail()`. SUBSCRIBER, DEMO, ENTERPRISE, and ADMIN are granted access. FREE and FREE_PENDING users are redirected to `/pricing`.

**How data gets here:** `WatchlistMatchingService` runs after each RSS harvest cycle (triggered from `FeedHarvestScheduler`) and writes new match records to `watchlist_matches`.

## How Data Gets In

The Content Area is fed by six background pipelines. All cron expressions are externalized to `application.yml`.

| Scheduler | When | What it produces |
|---|---|---|
| `FeedHarvestScheduler` | Daily 04:00 UTC (ACADEMIC/REGULATORY); every 4h (INDUSTRY) | New articles in `news_articles`; triggers topic summary generation, wiki compilation, and watchlist matching |
| `WebMonitoringScheduler` | Daily 05:00 UTC (competitor pages); 05:30 UTC (HuggingFace) | Additional articles in `news_articles` from web scraping |
| `ResearchHarvestScheduler` | Daily 04:00 UTC | Articles from Perplexity API (COMBINED mode) into `news_articles` |
| `RegulatoryHarvestScheduler` | Daily 04:30 UTC | New records in `regulatory_events` from FDA and CMS APIs |
| `TrendDetectionScheduler` | Weekly, Sunday 08:00 UTC | One new record in `trend_snapshots` per run |
| `NewsletterGenerationScheduler` | Daily 00:00 UTC | One new DRAFT record in `newsletter_runs` |

After each RSS harvest, `FeedHarvestScheduler` also cascades synchronously through:
1. `TopicSummaryGenerationService` -- updates `topic_summaries`
2. `WikiCompilationAdapter` -- updates `wiki_pages`, `wiki_contradictions`, `wiki_source_refs`, `wiki_page_revisions`
3. `WatchlistMatchingService` -- writes new records to `watchlist_matches`

## Cross-References

- The **Regulatory Watch** widget on `/dashboard` links to the full regulatory page at `/dashboard/regulatory`.
- The **Legal Pulse** widget on `/dashboard` pulls from the `"AI Healthcare Legal"` topic in `news_articles` -- the same articles visible in full at `/dashboard/legal` (Legal Timeline area).
- The **Trending Now** widget on `/dashboard` uses the same `trend_snapshots` data that powers `/dashboard/trends`.
- Wiki source provenance on `/wiki/{slug}` links back to original articles -- the same records browsable at `/dashboard/news` and `/dashboard/articles`.
- `/wiki` has an undocumented `/wiki/ask` endpoint (not in the nav) that converts wiki pages into pseudo-articles and calls AI search adapters, cross-referencing the AI Search feature (`/research/ai-search`).
- Sending a newsletter run via `/newsletter/runs/{runId}/send` queries active subscribers from the `subscribers` table -- the same data managed in the Admin area (`/admin`).
- Watchlist item-to-article links on `/watchlist` resolve via `news_articles` and link out to original source URLs.
- Trend signals on `/dashboard/trends` include `ScoredArticle` references that link to individual articles in the news feed.

## Known Limitations

**Fading and new trends are not computed.** `TrendDetectionService.detectTrends()` only populates the `risingTopics` list. The `TrendSnapshot` record has fields for `fadingTopics` and `newTopics`, and the templates have cards for them, but both lists are always empty. This has been the state since the Trends slice was built.

**Trend snapshot lookup is a full table scan.** `/dashboard/trends/history/{epochMillis}` loads all snapshots from the database and scans them in memory to find a match by epoch millisecond. As weekly snapshots accumulate, this will get slower.

**Wiki N+1 queries.** Two pages have N+1 patterns:
- `/wiki/{slug}` resolves each related page via a separate `WikiQueryPort.getPage()` call
- `/wiki/contradictions` resolves each page title via a separate `WikiQueryPort.getPage()` call per contradiction

Both are low-traffic pages today, but performance will degrade if either the related-pages list or the contradiction backlog grows large.

**Wiki source filtering is silent.** When rendering source provenance on `/wiki/{slug}`, the code silently drops: (a) article IDs starting with `"CBM"` (Google News base64-encoded IDs), (b) IDs longer than 200 characters, and (c) any source with no resolvable URL in `news_articles` and no `pubmed-` prefix. There is no "N sources could not be resolved" indicator on the page, so the provenance table may appear sparser than the underlying data.

**Dashboard article search has no tier gate and no login requirement.** Unauthenticated users who access `/dashboard?q=` can search the full article corpus. This may be intentional as an SEO surface but is worth tracking.

**`/dashboard/search` has no tier gating.** Any authenticated user, including FREE tier, can use the full date-range search form against the complete article corpus.

**`/dashboard/news` silently drops one title.** The controller hardcodes exclusion of the exact title string `"Anthropic Healthcare AI"`. Any article with that precise title -- including a legitimate one -- will be invisible on this page.

**Newsletter editor does not enforce DRAFT-only editing.** `NewsletterPreviewController.editRun()` loads and renders any run regardless of status. The TinyMCE editor will be presented even for SENT or ARCHIVED runs. The template may visually disable the controls, but the `POST .../save` endpoint does not check status before writing.

**Trend fallback path is more restrictive than the normal path.** When no persisted snapshot exists (e.g., before the first Sunday scheduler run on a fresh install), SUBSCRIBER and DEMO users get `fullAccess=false` even though they would normally have full access. They are treated the same as FREE users until the weekly scheduler runs and produces a snapshot.

**Dashboard watchlist cap vs. watchlist page cap differ.** The dashboard shows a maximum of 5 watchlist matches; the `/watchlist` page shows up to 50. Users with high-volume watchlists will see a much smaller picture on the dashboard than on the dedicated page.
