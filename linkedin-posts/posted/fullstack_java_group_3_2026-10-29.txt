Every endpoint in this app starts as a YAML edit, not a Java method. I write the OpenAPI spec first — request/response shapes, field types, required fields — then generate the DTOs from it. Controllers implement the generated delegate interface. Nobody hand-writes a DTO that's supposed to match the spec; the spec IS what generates it, so drift between "what the docs say" and "what the code actually returns" isn't physically possible without a Maven build failing.

The payoff shows up specifically at the full-stack boundary: when a frontend consumer (internal UI, external API client, doesn't matter) is coded against the spec, the backend literally cannot silently return a different shape without the generated interface changing first — which is a compile error, not a runtime surprise discovered three sprints later.

It's more upfront ceremony than just writing a controller method and letting the DTO shape emerge organically. For an API with real consumers, I'll take the ceremony every time over "wait, when did this field get renamed?"

For the full-stack folks here: spec-first or code-first — and has drift between docs and implementation ever actually bitten you?
