Not me. Claude. Autonomously.

Here's what actually happened in the DEBUG log:

→ Claude received: "Draft LinkedIn and Facebook posts from today's market digest."
→ Claude called: getDigestEntries("2026-09-28") → 8 ranked entries returned
→ Claude called: getCompanyArticles("Epic Systems") → 5 recent headlines
→ Claude wrote: LINKEDIN_BODY: ... FACEBOOK_BODY: ... RATIONALE: ...

The old version of this feature was 80 lines of Java deciding exactly what data to pre-load. The agent version is a system prompt, two @Tool methods, and a parser.

The difference isn't code volume. It's who decides what to fetch.

Old version: me, in Java, before the call.
New version: Claude, at runtime, based on the question.

That shift is what "agent" actually means in practice. Not a chatbot. A system that determines its own information-gathering path.

Built with Spring AI @Tool on a Spring Boot app tracking 57+ healthcare AI sources daily.

I spent part of the weekend teaching Claude to use tools — and it was one of those moments where a technology concept stops being theoretical.

What I built: a feature where Claude autonomously decides which data to pull from the database before drafting social posts. Not me picking which queries to run. Claude, at runtime, deciding it needs the market digest → fetching it → deciding it wants more context on a specific company → fetching that too → then writing.

The moment it clicked: watching it in the DEBUG logs. You can see Claude request a tool call, see the data come back, see it reason, call another tool, and then produce the output. That sequence IS the agent loop.

Before: 80 lines of Java deciding exactly what to pre-load.
After: a system prompt and two database tools. Claude handles the rest.

This runs inside a Spring Boot app tracking 57+ healthcare AI sources daily. If you want to see what it produces when it runs against real market data: app.bigskylabs.ai
