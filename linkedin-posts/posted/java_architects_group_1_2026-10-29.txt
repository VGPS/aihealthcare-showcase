A question I had to solve without reaching for Redis or Quartz Clustered: how do you run a per-minute cron sweeper across multiple app instances and guarantee each scheduled job fires exactly once?

The answer that's worked for a year: push the schedule state into Postgres and make the "claim" step a conditional UPDATE.

```
UPDATE schedules
SET next_run_at = :newNextRunAt
WHERE schedule_id = :id AND next_run_at = :observedNextRunAt
```

Every app instance runs the same per-minute sweep: query for schedules where `next_run_at <= now()`, then try to claim each one with that conditional UPDATE. Only one instance's UPDATE affects a row — the others get zero rows affected and move on. No distributed lock, no leader election, no extra infrastructure. Postgres's row-level write consistency does the whole job.

The detail that matters most: `next_run_at` advances *inside* the claim, before the job runs. If the job is slow or crashes, the next sweep can't double-fire it — the row already shows a future run time.

I run this for scheduled data exports and it hasn't double-fired or dropped a run once since going to a two-instance deploy.

For the architects here: if you've needed exactly-once scheduling across instances, did you reach for a DB-claim pattern like this, or something heavier (Quartz, Temporal, ShedLock)? Curious what tradeoffs pushed the decision.

--- STRATEGY NOTES ---

- This group pushes back on claims — be ready to defend "exactly once" precisely: it's exactly-once *delivery of the claim*, not exactly-once *job completion* (a job can still fail after being claimed — that's handled by a separate reaper, not this post's scope — don't overclaim if pressed).
- Likely pushback: "why not ShedLock/Quartz Clustered?" — honest answer is solo-dev simplicity: one less dependency, and Postgres is already the system of record.
