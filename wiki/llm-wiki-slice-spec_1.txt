## Context and intent

The newsletter currently summarizes each harvest cycle's articles in isolation. This slice adds a persistent, LLM-maintained wiki so drafting can use longitudinal context ("this reverses the FDA's March guidance"). Design goals, in priority order:

1. **Provenance is first-class.** Every wiki claim traces back to harvested `NewsArticle` records.
2. **Contradiction tracking is first-class.** Reversals and conflicts are structured data, not prose.
3. **Compilation is observable.** Every run produces a `CompilationReport` suitable for demos and logging.
4. **Raw sources are immutable.** The wiki layer never mutates `NewsArticle` records.

## Increment 1 — Domain records

Create the following Java records in the domain module, following all conventions in `docs/CONVENTIONS.md` (class-level Javadoc with `@author Bill Blackmon`, `@version`, `@since`, `@updated`; records for immutable data).

**`SourceRef`** — record linking a wiki claim to its origin:
- `String articleId` (references `NewsArticle`)

**`WikiPage`** — record:

- `Instant runStartedAt`, `Instant runCompletedAt`
- `int articlesProcessed`

## Product thesis (context for all design decisions)

Long-term, the compiled wiki — the reference asset — matters more than "today's news." The newsletter is the weekly delivery vehicle, but the durable value (and eventual paying traction) is the accumulated, verified, structured knowledge base. Timeline expectation is a year or more before real traction; design for compounding, not for launch-week polish. When a design tradeoff arises between "faster weekly output" and "richer, better-provenanced wiki," prefer the wiki. This thesis should be reflected in Javadoc and architecture docs where relevant.

**Slice W5 — Reader-facing provenance.** Surface `SourceRef` links in the rendered newsletter (Thymeleaf templates): every claim links to its FDA/PubMed/ClinicalTrials origin. Trust differentiator specific to healthcare. Also consider a public read-only wiki view as a future web-module feature.

**Slice W6 — Wiki linter.** A scheduled agent pass that checks: orphaned pages, broken `relatedSlugs` cross-references, stale pages (no update since threshold), missing provenance, and (deep mode) factual conflicts between tag-overlapping pages. Output is a lint report persisted alongside `CompilationReport`. Doubles as a strong teaching chapter.

**Slice W7 — Evaluation harness.** RAGAS-style faithfulness/relevance evals run against wiki-grounded summaries, behind the existing AI-profile flag to control cost. Persist scores over time; eventually publish headline numbers ("summaries verified against sources") as a credibility claim.

**Slice W8 — Domain-pack extraction (multi-vertical readiness).** Enforce and formalize the separation between the domain-agnostic engine and vertical-specific content so the platform can be replicated for other verticals (e.g. AI Finance, AI Education) with minimal code changes. Deliverables: (1) an architecture test or review checklist asserting no healthcare-specific strings, sources, or prompts exist in `domain`, `application`, or core `infrastructure` code; (2) a per-vertical configuration profile (YAML) holding topics, feed URLs, and API endpoints; (3) a `domain-pack/` Skills folder externalizing the editorial intelligence as prose — compilation prompt (entity-page style, per-domain contradiction criteria), editorial voice, domain glossary, linter rules, and provenance/citation standards; (4) documentation of the replication recipe: new vertical = skill folder + YAML profile + 1–2 harvesting adapters + Thymeleaf theme. Note: the compiled wiki itself intentionally does not transfer — each vertical accumulates its own knowledge asset, making replication a product line rather than dilution. This slice is ongoing in spirit: from W2 onward, prefer designs that keep healthcare specifics out of core modules so W8 is an extraction, not a rewrite.
