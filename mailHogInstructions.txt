MailHog is a good choice for local Spring Boot development in IntelliJ, and your mail settings should live in application.yml or application.properties with a separate profile for local testing.

MailHog setup
The easiest way to run MailHog is with Docker: it exposes SMTP on localhost:1025 and the web UI on http://localhost:8025. MailHog also has an official Docker Hub image, and Docker-based install is the most common approach for local development.

Example command:

bash
docker run -d --name mailhog -p 1025:1025 -p 8025:8025 mailhog/mailhog
That starts a local SMTP server your Spring Boot app can send to.

Spring Boot config
For local testing, point Spring Boot at MailHog in a dev profile. A typical application.yml looks like this:

text
spring:
  mail:
    host: localhost
    port: 1025
    username:
    password:
    properties:
      mail.smtp.auth: false
      mail.smtp.starttls.enable: false
MailHog does not require authentication for the default local setup, so the app just needs the host and port. Keep these settings separate from production so you can switch to SES later without changing code structure.

IntelliJ workflow
Run MailHog first, then start your Spring Boot app from IntelliJ. If both are running locally, your app will send mail to MailHog instead of a real inbox, and you can inspect messages in the web UI at http://localhost:8025. This is ideal while your newsletter code is still under development because no real emails are sent.

Suggested project layout
Use profiles so the same app can work in dev and production.

application.yml for shared settings.

application-dev.yml for MailHog.

application-prod.yml for Amazon SES later.

That keeps your newsletter code clean and lets you test template rendering, recipient loops, and error handling locally before AWS is ready.
